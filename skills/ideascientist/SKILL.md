# IdeaScientist 本地科研构思

将一个明确的问题和挑战转成有文献证据、可实施、可否证的研究方案。默认使用当前 Codex 模型、可用搜索和本地文件；这是论文方法的本地适配，未加载作者训练的 LoRA、完整 Idea Vault 或论文评测器，不承诺复现其分数。

## 研究判断原则

### 思考 idea

我们并不追求“绝对原创”或“从未有人做过”的完美 idea，也不要因为已有相似工作就过度防御性地否定一个方向。已有方法在相关问题上的尝试，并不意味着这个思路失去了价值；只要我们能够与现有工作形成清晰且有意义的差异，进一步推进、完善或深化某个思想，解决已有方法的不足，或者从新的视角重新组织问题并讲出一个更完整、更有说服力的故事，这个 idea 就是可行的。判断的重点应是是否存在明确的新增贡献和进一步探索空间，而不是是否完全没有先例。

这里的“可行”指值得进一步研究，效果仍需验证。新的视角或更完整的故事应落实到问题理解、机制、理论或验证上的实质推进；单纯改名、换叙述或润色表述不足以支撑 novelty。

### 检查 idea novelty

对于我提供的 idea，默认应优先尝试保留和发展它，而不是因为存在相似工作就轻易否定。首先，请系统调研一批与该 idea 最接近的论文，并尽可能深入阅读其核心方法、问题设定、技术细节和贡献边界，避免仅凭标题、摘要或表面相似性做出猜测。基于这些工作，分析我们的 idea 与现有方法之间真正的差异，并尝试用一段清晰、有说服力的话论证其 novelty，包括我们具体新增了什么、推进了什么，以及为什么这种差异是有意义的。但不要为了保留 idea 而强行制造 novelty：如果调研后发现与已有工作在核心问题、关键方法和主要贡献上的确存在不可绕过的高度重合，已经难以形成实质性区分，则应停止论证，并明确指出与哪些工作严重撞车、具体重合在哪里，以及为什么现有差异不足以支撑一个可信的 novelty claim。

上述“我提供的 idea”指当前用户提供的 idea。忠实记录原始构思，区分用户已有贡献、检索后提出的改进以及尚待验证的差异；不要把另一个新方向悄悄替换成用户的原始 idea。

## 开始与模式

- 从用户描述和已提供材料提取：输入、期望输出、具体失败案例、核心挑战、计算或数据约束。已有信息足够就开始；只询问会改变方向的缺失信息。
- 默认是**当前文献构思**，检索截止当前日期。用户要求历史回测时，采用其指定的严格截止日期（不含当天），隔离目标论文及截止后材料；日期检查以实际读取版本的公开日期为准，不能用初次发表日期替代。
- 用户给定种子论文时，可用于当前构思；若它是回测的隐藏目标，不得读取其方法来生成“预测”。已经读过目标方法就说明污染，不能声称盲测。模型记忆造成的时间污染也无法靠提示消除。
- 从零构思时按“缺口 → 机制发展／迁移 → novelty 核查与反驳验证 → 方案”推进。用户已有 idea 时，先忠实重述它，再从最近邻调研和差异分析开始，围绕其核心发展；不要求另造 idea 或强行加入跨领域迁移。只请求 novelty 检查时，交付比较、论证或撞车结论即可，无需扩展成完整 proposal。
- 默认在当前任务内依次执行这些角色；用户授权并行代理且工具可用时，才把独立阅读或独立轴的调查交给代理。单上下文模式没有原版的工具级角色隔离，不能声称已隔离。
- 为完整研究任务创建用户工作区下独立的 `ideascientist-runs/<日期>-<主题>/`，不要把输出写进安装目录。保留已有研究，不覆盖旧运行。快速讨论可以直接回答，并省略文件持久化。

## 1. 定义问题并建立证据记录

用 `problem.md` 固定问题、挑战、约束、模式和截止日期；`plan.md` 只记当前研究轴、选择、版本和下一步。

检索使用宿主实际提供的浏览器、搜索工具或用户文献库。原项目的 `keyword_search`、`read_paper` 等名称不是本插件提供的工具，不得凭空调用。联网不可用时，先分析已有正文；证据不足的结论明确标成假设。

为要用于结论的论文阅读相关正文，通常带 1–5 个具体问题：机制是什么、依赖什么假设、失败何时发生、限制是实测还是推断。累计保存 `papers/P001.md` 等摘要与章节／页码；不把标题、摘要或搜索片段当作方法级证据。新增阅读问题追加到原摘要，不删除旧答案。引用格式、证据账本和输出规范见 [evidence-and-artifacts.md](references/evidence-and-artifacts.md)。

## 2. Gap finder：找方法缺口

每次聚焦一个挑战轴，用该领域的准确术语检索同问题、同挑战的工作。对最接近的方法进行正文核查和引用追踪。查询数量随覆盖情况调整，不把数量当质量指标。

在 `gaps.md` 中先概括已有机制，再为每个有根据的缺口给出：

- 具体缺口和被挑战的假设。
- 最接近的方法及其已解决部分、共同剩余不足；通常至少两篇读过的论文。若只有一篇，交代检索范围及为什么它是唯一近邻。
- 方法层面的原因：算法、目标函数、归纳偏置、表示、信用分配或扩展性等。
- 解决它为什么重要，以及什么可观察证据能证明它被解决。

每轴保留最多两个扎实缺口；没有证据就输出零个。数据集缺失、“还没人试过”、单纯换场景或缺少排行榜成绩，不自动构成方法缺口。用户明确要数据集或评测选题时可以适配，但说明这扩展了原论文的方法创新范围。

## 3. Innovator：发展或迁移机制

从已成立的缺口选择一个，先形成一个候选再深入，不机械堆叠多个点子。用户已有 idea 时，以其核心为首个候选，优先寻找可以推进、完善或深化的部分；已有先例是比较和发展的起点，不是自动否决的理由。

需要寻找借鉴机制时，用抽象挑战而非目标领域的专用词搜索其他领域：例如资源分配、部分可观测性、组合泛化、延迟、噪声估计。可优先探索跨领域联系，也允许推进域内机制；不以跨领域为合格门槛。必须阅读实际借用的来源机制及最接近目标领域方法的正文。

在 `candidates.md` 给候选编号 C1、C2……并记录：

- 1–2 句话说明直觉；关联 gap。
- 来源论文、已有机制及拟推进之处；有借用机制时说明它在原领域成立的条件。
- **对应关系**：发生迁移时，源问题中的对象、状态、约束、更新／反馈，在目标问题中各对应什么；直接发展域内 idea 时说明已有机制如何改变。
- 机制改进或迁移为何可能成立；哪些条件仍是假设；最可能失败在哪里。
- 与具名最近邻方法的实质差异；属于新方向、远距离组合还是补强已有联系。

本阶段解释机制即可，详细方程、架构和实验交给方案阶段。新候选可以改进旧候选，但必须写明改变了什么。

## 4. Reviewer：发展 idea 并核查 novelty

先系统调研一批最近邻论文，结合“核心问题 + 关键方法”“来源机制 + 目标任务”、术语变体和引用追踪扩展覆盖。深入阅读最相关工作的核心方法、问题设定、技术细节和贡献边界；核查实际假设、优化目标、信息条件、算法机制和验证范围，不能从相似名称推断方法相同。

逐项比较已有工作做到了什么、我们的真实新增是什么、该差异解决了什么不足或带来什么新理解，以及如何验证其意义。将可发展的实质差异与仅换名称、场景或叙述的表面差异分开。对可修复的弱点先尝试完善核心构思，同时保留来源核查、迁移条件检查和最强反对意见。

在 `scores.md` 中给出最近邻比较表和证据。若支持实质新增，用**一段清晰、有说服力的话**论证 novelty，说明相对于具名工作具体新增／推进了什么、为什么有意义，以及论证依赖的条件；再给出最小验证建议。若证据不足，明确哪些差异待核实，不把“尚未确认”写成“没有 novelty”。具体输出规范见 [evidence-and-artifacts.md](references/evidence-and-artifacts.md)。

审查结论使用 `survive`、`revise` 或 `reject`：有明确且有意义的差异可 `survive`；有可发展空间但需要证据或方法完善时用 `revise`，指出下一步；只有核心假设被证据否定且无法修复，或经深入比较确认在核心问题、关键方法和主要贡献上存在难以绕过的高度重合、现有差异不足以形成实质贡献时，才 `reject`。严重撞车时停止为当前版本论证 novelty，列出具名论文、具体重合和差异不足的原因；后续转向应明确作为新的修改建议，不能替原版本强行辩护。

`survive` 只表示值得进入实验设计，不代表已证明有效或全局新颖。重复检索不再改变证据时停止，说明覆盖范围和剩余不确定性。未找到可信候选时交付事实与原因，不强行生成“创新”。

## 5. Report writer：写成可检验的方案

有通过审查的候选后，输出中文 `proposal.md` 和结构化 `report.json`。英文术语按需保留。全文结构遵循 [report.schema.json](assets/report.schema.json)，填写问题、创新、方法、模型／训练、最近邻比较、评测、可证伪预测和限制；不适用项解释原因。

- 每条方法描述应让研究者知道模块输入输出、算法、训练目标和执行顺序。
- 基线、数据集和现成模型必须可核实；新设计的评测集显式标记为拟构建。
- 先设计能推翻核心假设的最小实验，再列完整实验；给出对照、指标、消融、成本估计依据和停止条件。成本未知就说明，别制造精确预算。
- 每个核心预测配 `kill_condition`：出现什么观察将否定它。预期值与计划参数不能写成已测结果。
- 在 `proposal.md` 保留一段经最近邻比较支撑的 novelty 论证；`report.json` 的 `key_novelty` 和 `comparison_to_sota` 反映相同的实质新增及其意义。结论限定在已检索范围；查不到不等于不存在，相似工作存在也不等于当前 idea 无价值。

按照证据规范写 `sources.json`，在报告字符串中用 `[P001]` 引用，在面向用户的文档中把编号链接到原文。交付前运行：

```bash
python3 <本技能目录>/scripts/audit_report.py <运行目录>
```

有历史截止日期时追加 `--cutoff YYYY-MM-DD`。此检查验证结构、引用解析、正文阅读记录、摘要存在和版本日期；**不验证文献真伪、引用蕴含、创新性或方法有效性**，这些仍需阅读和实验。工具缺失时人工核查并注明未运行自动检查。

交付时先给最值得推进的方案与理由，再给证据、最小实验和待解决问题，并链接成果文件。不要把一次自评打分当作论文的验证结果。
