# IdeaScientist 本地科研构思

将一个明确的问题和挑战转成有文献证据、可实施、可否证的研究方案。默认使用当前 Codex 模型、可用搜索和本地文件；这是论文方法的本地适配，未加载作者训练的 LoRA、完整 Idea Vault 或论文评测器，不承诺复现其分数。

## 开始与模式

- 从用户描述和已提供材料提取：输入、期望输出、具体失败案例、核心挑战、计算或数据约束。已有信息足够就开始；只询问会改变方向的缺失信息。
- 默认是**当前文献构思**，检索截止当前日期。用户要求历史回测时，采用其指定的严格截止日期（不含当天），隔离目标论文及截止后材料；日期检查以实际读取版本的公开日期为准，不能用初次发表日期替代。
- 用户给定种子论文时，可用于当前构思；若它是回测的隐藏目标，不得读取其方法来生成“预测”。已经读过目标方法就说明污染，不能声称盲测。模型记忆造成的时间污染也无法靠提示消除。
- 按依赖顺序执行“缺口 → 迁移 → 审查 → 方案”。默认在当前任务内依次执行这些角色；用户授权并行代理且工具可用时，才把独立阅读或独立轴的调查交给代理。单上下文模式没有原版的工具级角色隔离，不能声称已隔离。
- 为完整研究任务创建用户工作区下独立的 `ideascientist-runs/<日期>-<主题>/`，不要把输出写进安装目录。保留已有研究，不覆盖旧运行。快速讨论可以直接回答，并省略文件持久化。

## 1. 定义问题并建立证据记录

用 `problem.md` 固定问题、挑战、约束、模式和截止日期；`plan.md` 只记当前研究轴、选择、版本和下一步。

检索使用宿主实际提供的浏览器、搜索工具或用户文献库。原项目的 `keyword_search`、`read_paper` 等名称不是本插件提供的工具，不得凭空调用。联网不可用时，先分析已有正文；证据不足的结论明确标成假设。

为要用于结论的论文阅读相关正文，通常带 1–5 个具体问题：机制是什么、依赖什么假设、失败何时发生、限制是实测还是推断。累计保存 `papers/P001.md` 等摘要与章节／页码；不把标题、摘要或搜索片段当作方法级证据。新增阅读问题追加到原摘要，不删除旧答案。引用格式、证据账本和输出规范见 [evidence-and-artifacts.md](references/evidence-and-artifacts.md)。

## 2. Gap finder：找方法缺口

每次聚焦一个挑战轴，用该领域的准确术语检索同问题、同挑战的工作。对最接近的方法进行正文核查和引用追踪。查询数量随覆盖情况调整，不把数量当质量指标。

在 `gaps.md` 中先概括已有机制，再为每个有根据的缺口给出：

- 具体缺口和被挑战的假设。
- 最接近的方法及其已解决部分、共同剩余不足；通常至少两篇读过的论文。若只有一篇，交代检索范围及为什么它是唯一近邻。
- 方法层面的原因：算法、目标函数、归纳偏置、表示、信用分配或扩展性等。
- 解决它为什么重要，以及什么可观察证据能证明它被解决。

每轴保留最多两个扎实缺口；没有证据就输出零个。数据集缺失、“还没人试过”、单纯换场景或缺少排行榜成绩，不自动构成方法缺口。用户明确要数据集或评测选题时可以适配，但说明这扩展了原论文的方法创新范围。

## 3. Innovator：迁移机制

从已成立的缺口选择一个，先形成一个候选再深入，不机械堆叠多个点子。

用抽象挑战而非目标领域的专用词搜索其他领域：例如资源分配、部分可观测性、组合泛化、延迟、噪声估计。优先跨领域，允许有实质变化的域内迁移。必须阅读来源机制和最接近目标领域方法的正文。

在 `candidates.md` 给候选编号 C1、C2……并记录：

- 1–2 句话说明直觉；关联 gap。
- 来源论文、借用机制及它在原领域成立的条件。
- **对应关系**：源问题中的对象、状态、约束、更新／反馈，在目标问题中各对应什么。
- 迁移为何可能成立；哪些条件仍是假设；最可能失败在哪里。
- 与具名最近邻方法的实质差异；属于新方向、远距离组合还是补强已有联系。

本阶段解释机制即可，详细方程、架构和实验交给方案阶段。新候选可以改进旧候选，但必须写明改变了什么。

## 4. Reviewer：主动尝试推翻

用“来源机制 + 目标任务”的组合重新搜索，寻找已经实现相同方案的工作。核查：来源是否被准确理解、映射是否具体、条件是否能迁移、差异是否真实、是否有方法贡献。仅复述候选的优点不算审查。

在 `scores.md` 记录证据、最强反对意见，以及 `survive`、`revise` 或 `reject`。`survive` 只表示可以进入实验设计，不代表已经证明有效或全局新颖。若可修复，修正最薄弱的一点再审查；若核心假设失败或已被完成，放弃此候选。重复检索不再改变证据时停止，并说明剩余不确定性。未找到可信候选时交付缺口与阻塞证据，不能强行生成“创新”。

## 5. Report writer：写成可检验的方案

有通过审查的候选后，输出中文 `proposal.md` 和结构化 `report.json`。英文术语按需保留。全文结构遵循 [report.schema.json](assets/report.schema.json)，填写问题、创新、方法、模型／训练、最近邻比较、评测、可证伪预测和限制；不适用项解释原因。

- 每条方法描述应让研究者知道模块输入输出、算法、训练目标和执行顺序。
- 基线、数据集和现成模型必须可核实；新设计的评测集显式标记为拟构建。
- 先设计能推翻核心假设的最小实验，再列完整实验；给出对照、指标、消融、成本估计依据和停止条件。成本未知就说明，别制造精确预算。
- 每个核心预测配 `kill_condition`：出现什么观察将否定它。预期值与计划参数不能写成已测结果。
- 新颖性结论限定在已检索范围；查不到不等于不存在。

按照证据规范写 `sources.json`，在报告字符串中用 `[P001]` 引用，在面向用户的文档中把编号链接到原文。交付前运行：

```bash
python3 <本技能目录>/scripts/audit_report.py <运行目录>
```

有历史截止日期时追加 `--cutoff YYYY-MM-DD`。此检查验证结构、引用解析、正文阅读记录、摘要存在和版本日期；**不验证文献真伪、引用蕴含、创新性或方法有效性**，这些仍需阅读和实验。工具缺失时人工核查并注明未运行自动检查。

交付时先给最值得推进的方案与理由，再给证据、最小实验和待解决问题，并链接成果文件。不要把一次自评打分当作论文的验证结果。
